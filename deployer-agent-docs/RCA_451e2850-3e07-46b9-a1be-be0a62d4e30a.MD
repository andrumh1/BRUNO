# Informe de infraestructura — BRUNO / premium-launch-13 (brunocard.com)

Consulta de solo lectura. No se cambió nada. Objetivo: datos de infra de producción para
decidir cómo autenticar Firebase Admin SDK (FCM) SIN clave JSON de cuenta de servicio.

## HALLAZGO PRINCIPAL (crítico): producción NO está en Google Cloud

El preview que el cliente inspeccionó corre en GCE/GKE, pero **el pod de producción corre en AWS**,
no en Google Cloud. Preview ≠ producción a nivel de nube. Evidencia (describe_deployment_state +
get_pod_events, autoritativa):

- run_image activo: `287883095218.dkr.ecr.us-west-2.amazonaws.com/customers-app@sha256:98fca5...`
  → AWS ECR, región **us-west-2 (Oregon)**.
- architecture: **arm64** (Graviton).
- target_cluster: `deployment-cluster-05`, namespace de producción: `customers-app`.
- 2 réplicas Running, tier_0, run status success.

Runs anteriores (≤ 2026-10-11) usaban `us-central1-docker.pkg.dev/emergent-default/...` (amd64,
GCP Artifact Registry). Es decir: la app fue **migrada de GKE/GCP (us-central1) a AWS EKS
(us-west-2) entre el 11 y el 15 de oct**. Cualquier supuesto de "prod = GKE / proyecto
emergent-default / GCE" quedó obsoleto.

## Importante sobre el alcance de lo que pude verificar

- No tengo exec dentro del pod de producción. Solo puedo leer logs/eventos de prod.
- La única superficie con shell (sandbox eph) se programó en **GKE** (`emergent-default`,
  us-central1, nodo Autopilot `gk3-emergent-default-clu-...`, x86_64) — es infra de
  SANDBOX/preview, NO el nodo de producción (que es AWS arm64). Por tanto, todo sondeo de red
  del sandbox describe GKE-emergent, no AWS-producción.
- Conclusión: las preguntas de red de PRODUCCIÓN (metadata server, token proyectado, IP de salida,
  identidad federable) NO pueden confirmarse con mis herramientas. Las marco UNVERIFIED y explico
  lo inferido.

## Respuestas punto por punto

**1. Nube/región/proyecto del pod de producción.**
AWS, región **us-west-2**, cluster `deployment-cluster-05` (estilo EKS), namespace `customers-app`,
arquitectura arm64. NO hay proyecto de Google Cloud alojando el pod de producción. (El proyecto
`emergent-default` en us-central1 aún aloja el preview/sandbox, pero NO producción.) VERIFICADO.

**2. Metadata server GCE / Workload Identity / identidad de ADC en prod.**
UNVERIFIED en prod (sin exec). En el SANDBOX (GKE, no prod) el metadata GCE responde y ADC
devuelve `emergent-default.svc.id.goog` (WI pool de Emergent) — irrelevante para prod y además
pertenece a Emergent, no al cliente. Como producción es AWS, NO existe metadata server GCE útil;
`169.254.169.254` en AWS es el IMDS de AWS, y google-auth/ADC NO obtendría de ahí una identidad
Google. Inferencia: **en producción ADC no produce credenciales de Google** por defecto.

**3. Token K8s proyectado con issuer OIDC público (para WIF).**
UNVERIFIED en prod. En el sandbox (GKE) sí hay token proyectado en
`/var/run/secrets/kubernetes.io/serviceaccount/token`, issuer
`https://container.googleapis.com/v1/projects/emergent-default/locations/us-central1/clusters/emergent-default-cluster`,
subject `system:serviceaccount:agent-eph:default` — issuer GKE discoverable públicamente, pero es
infra de Emergent/sandbox. En prod (AWS EKS) normalmente también se proyecta un token y EKS expone
un issuer OIDC público (`oidc.eks.us-west-2.amazonaws.com/id/...`), PERO no pude confirmar que el
pod de prod lo monte ni su issuer/audience/subject. Aunque existiera, issuer/subject los controla
Emergent y el `subject` sería run-scoped (namespace `customers-app`, SA probablemente `default`),
frágil entre redeploys. WIF requeriría coordinación con la plataforma (Emergent).

**4. Env vars multilínea / JSON ~2-3 KB / mecanismo de secretos distinto a .env.**
Los secretos de producción se guardan cifrados en el store de la plataforma y se inyectan como
**variables de entorno** (pestaña Secrets). Un JSON de ~2-3 KB en una sola línea cabe sin problema;
el tamaño no es una restricción práctica. El propio código ya usa esta vía:
`utils/native_push.py` lee `FIREBASE_SERVICE_ACCOUNT_JSON` y hace `json.loads()` (si falla, intenta
tratarlo como ruta a archivo). Recomendación: guardar el JSON **compacto en una sola línea**
(o base64) — la pestaña Secrets es de una línea. **No hay** mecanismo de secreto montado como
archivo distinto a las env vars. NOTA: `FIREBASE_SERVICE_ACCOUNT_JSON` NO está configurado hoy en
prod (no aparece en list_secrets) → el push nativo está actualmente deshabilitado.

**5. IP de salida fija/conocida en prod.**
UNVERIFIED / NO garantizable. No tengo herramienta para leer la IP de egreso de prod; la del
sandbox (34.55.174.138, Google) es de GKE y no aplica a AWS. Prod sale por el NAT del cluster AWS
us-west-2; no está garantizado que sea una IP única fija y la propia migración GCP→AWS demuestra que
la identidad de egreso puede cambiar por completo. **Riesgoso** anclar un allowlist de IP de una
API key de Google al egreso de prod.

**6. Certificado/identidad gestionada por la plataforma para llamar APIs de Google por el cliente.**
No hay ninguna credencial de Google expuesta a la app para actuar en nombre del cliente. La única
identidad de plataforma visible es la WI SA de Emergent (`emergent-default.svc.id.goog`) en el
sandbox GKE — es de Emergent, no del cliente, y no está disponible en los pods AWS de prod.
Cualquier federación (WIF) la configuraría el cliente confiando en un issuer OIDC controlado por
Emergent, lo que exige que Emergent publique issuer/subject estables (conversación de
soporte/plataforma).

## Recomendación de camino keyless
El código solo soporta hoy un JSON crudo en `FIREBASE_SERVICE_ACCOUNT_JSON`. Para un flujo sin
clave hay que: (a) extender `utils/native_push.py` para aceptar ADC / credencial `external_account`
(WIF) — p.ej. `GOOGLE_APPLICATION_CREDENTIALS` apuntando a un config file de WIF, o
`initialize_app()` con ADC; y (b) que Emergent (plataforma) confirme/exponga el issuer OIDC y
subject estables del cluster de prod AWS + si hay IP de egreso fija. Sin esos datos de plataforma,
WIF no es accionable de forma fiable.
